## Outcome and rationale

State the change and why it matters in one sentence. Use “so that” to connect the work to the outcome it enables.

## Scope and constraints

Use short, labeled bullets for boundaries and material tradeoffs. Link to context the reader needs.

## Prerequisites

List what must be true before implementation starts. For changes to existing code, review the automated checks and identify gaps in the affected behavior. Add pin-down tests where needed and verify the baseline against the existing implementation.

## Acceptance criteria

Write a short, labeled bullet for each part of the outcome. Use plain language to say what changes and what users or callers should still be able to do. Include technical details when they help the reviewer verify the result.

### Automated coverage

Summarize what the checks cover, the before-and-after results where applicable, and any limits of the evidence.

### Reproduce the check

Give the checkout, setup, command or steps, and expected result so the owner can verify the behavior.

## Approvals and verification

- Owner approval of plan, intended behavior, and checks
- Owner decisions on material tradeoffs
- Verified revision and links to evidence
- Adversarial review, with reviewed revision and explicit PR and closure recommendations
- Owner sign-off on observed behavior
